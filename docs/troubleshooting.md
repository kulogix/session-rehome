# Troubleshooting

Every refusal says why, and nothing was changed when a command refuses. Find the message below.

## Installing

| You see | Do |
|---|---|
| `REFUSED: … exists and was not installed by this installer` | an older copy is in the way. `install.py --force` moves it to `~/.claude/skill-backups/` (nothing is deleted) |
| `looks like an earlier install of …, and both would load` / `an OLDER install is still present` | a folder of an earlier release (`claude-desktop-rehome`, `claude-session-transporter`) is still in the skills folder, and both copies would load. `install.py --force` moves it to `~/.claude/skill-backups/` (nothing is deleted) |
| `ccd-rehome: command not found` | the launcher folder is not on your `PATH`, or you installed without `--bin`. Re-run `install.py --bin ~/.local/bin` and add that folder to `PATH` |
| `could not create a symlink` (Windows) | use `install.py --copy` |
| the agent does not find the skills | start a new Claude Code session: skills are read when a session starts. `install.py --status` shows what is installed |

## One machine (`ccd-rehome`)

| You see | Do |
|---|---|
| `is running … Quit it` | quit that window (File > Quit), or `ccd-rehome quit work` on macOS / Linux |
| `Desktop ignored the quit signal` | quit it from its menu. If it is frozen, force-close it and start it again; your sessions on disk are safe |
| `refusing: this command is running INSIDE …` | you (or your agent) are inside that window; quit it yourself |
| `not signed in` | sign that window in, quit, re-run |
| `no org known for … in this profile`, `ambiguous: N orgs known for this account` | open the Code tab once while signed in, quit, re-run (or pass `--to-org`) |
| `matches 0 known accounts` | check the spelling with `ccd-rehome accounts`; the account must have been signed in once somewhere on this machine |
| `not a Desktop profile (no config.json)` | wrong folder, or that window was never started: start it once. A path you meant as a CLI home prints this too when the folder has none of `projects/`, `.claude.json`, `.credentials.json` and `settings.json`: check the path, or start Claude Code in it once (`CLAUDE_CONFIG_DIR=/path/to/home claude`) |
| `… does not exist` | the name or path names no folder: a window name that no profile root holds and no known window has (never started, misspelt, or in a folder the tool does not know), or a path (to a Desktop window or a CLI home) that is not there. `ccd-rehome profiles` lists what exists; register a window folder anywhere with `ccd-rehome profiles --add PATH`, or the folder that holds several with `ccd-rehome profiles --add-root DIR` ([multiple-instances.md](multiple-instances.md#your-own-folders)) |
| `` `…` is ambiguous: N Desktop profiles have that folder name: … `` | two folders fit that window name (two profile roots both hold a `work`, or two known windows are called `work`). Type the path of the one you mean; the message lists both |
| `` `cli:NAME` is ambiguous: N CLI homes have the folder name … `` | there is no `~/.claude-NAME`, and two known CLI homes are called `NAME` (or `.claude-NAME`). Type the path of the one you mean; the message lists both |
| `is a CLI home (a Claude Code config dir), not a Desktop profile` | the window name you typed is a folder in a profile root that is a CLI home. Name it by its path, or as `cli:NAME` |
| `cannot add …` / `cannot add the profile root …` (`profiles --add`, `--add-root`), with a reason such as `it is neither a Desktop profile (no config.json) nor a CLI home …` or `it does not exist` | `--add` takes one window folder (it has `config.json`: start the window once) or one CLI home; `--add-root` takes the folder that holds several. The message says which one fits. Nothing was changed |
| `is not registered with --add or --add-root` (`profiles --forget`) | that path was never added. If the message says how it is found (`found: shell file ~/.bashrc`, `found: env CCD_REHOME_PROFILES`), remove it there. Nothing was changed |
| `is the tool's state folder … (or inside it)` | the tool's own state folder (archives, the account registry) is never a window or a CLI home. Name another folder |
| `these conversations are open in another process` | the session is open in a terminal or another window: close it there |
| `cannot find the Desktop app` | start it yourself, or set `CCD_REHOME_DESKTOP=/path/to/app` |
| `MISMATCH  Desktop loaded …` (`verify`) | quit and start the window again, then verify again; if it persists, look at `ccd-rehome sessions work` for unreadable records |
| `Desktop has not logged loading … yet` (`verify`) | it is still starting: wait, open the Code tab, re-run |
| `DRIFT` (from `doctor` or a move) | a newer Desktop stores something the tool does not know. Update this project first. If it is still there, look at it with `--dry-run`, then use `--accept-drift` or report it (CONTRIBUTING.md) |
| `ERROR  …` and `refusing: the files are not in the format this tool knows` | a file is not in the expected format. Nothing was changed; please report it |
| `Cowork user data (spaces / agents / settings, Desktop 4.x)` (an `ERROR` of a move with `--include-cowork`) | Cowork spaces or agents hold data whose link to sessions is not understood yet. Code sessions move fine without `--include-cowork` |
| a session shows `transcript MISSING` | its conversation file is not on this machine (usually a session made elsewhere). Moving it is harmless, but it will not open |
| a session shows `in cli:work` | its Desktop record points at a conversation that lives in another CLI home, not in `~/.claude`, where Desktop looks for its conversations, so that window cannot open it. Copy the conversation into `~/.claude`: `ccd-rehome move cli:work --only CLI_ID --to-profile cli --copy`, where CLI_ID is the `CLI id` the flag shows (a move takes the conversation's id, not the record id in the first column); `ccd-rehome sessions PROFILE` prints that line for you, with the full ids. Use `--copy`, not a plain move: the other home is often a backup that kept an old conversation after `~/.claude`'s retention deleted it, and a moved copy that is re-dated is deleted from `~/.claude` again after `cleanupPeriodDays` without a new turn (one last continued in Desktop by a Claude Code before 2.1.248, by `desktopSessionCleanupPeriodDays` or by a managed `cleanupPeriodDays`), when the backup no longer has it. The undo of that copy works too (with a warning). Only if you started that window with `CLAUDE_CONFIG_DIR` set to that home does it read that home instead; the tool cannot see that. `ccd-rehome sessions PROFILE` also ends with a note when none of a window's records' conversations is in `~/.claude`, and `ccd-rehome status PROFILE` counts such records per home (`N of these records' conversations are only in cli:work, not in ~/.claude`; JSON `elsewhere`) |
| `is OPEN in …` (CLI move or rollback) | a live `sessions/<pid>.json` entry names the session: close that terminal session, then re-run |
| `… is open in another process` (CLI move or rollback) | another process (a terminal `claude`, a Desktop window) has the conversation file open. Nothing was changed. Close it there, then re-run |
| `is shown by Desktop profile …, and Desktop looks for its conversations in …: moving it out of … would leave that window without it; unregister it first` / `… (record … names it among its earlier conversations), and Desktop looks for its conversations in …: … would leave that window without it; use --copy` | a Desktop record (in any window) points at this conversation, which is in `~/.claude`: as its conversation, or as one of its earlier ones (`priorCliSessionIds`; the message then names the record). `~/.claude` named another way (a bind mount, `~/.Claude` on a case-insensitive disk) is still `~/.claude`: the tool compares folders, not names. The tool cannot see whether a window was started with `CLAUDE_CONFIG_DIR`, so it takes every window to read `~/.claude`, and the move would leave that window without it. Nothing was changed. For a record's own conversation: `ccd-rehome unregister PROFILE --only ID` first, or use `--copy`. For an earlier conversation, use `--copy` only: unregistering that record would also take its current conversation out of the window. A move INTO `~/.claude` is always allowed, and a move between two other homes goes ahead with a note |
| `already has a DIFFERENT transcript` | the target CLI home has another conversation with the same id. Nothing was changed; pick the right home, or remove the other copy yourself |
| `already has …, which a move never overwrites` (CLI move) | the target home already has one of the session's files (its sidecar folder, `tasks/<id>`, `file-history/<id>` or a todo file) but not its conversation. Nothing was changed. Look at that file in the target, keep or remove it yourself, then run the move again |
| `has a transcript in N project folders of …` | the same conversation id is filed under two project folders of the source home, and `claude --resume` cannot pick one. Nothing was changed. Compare the two, move all but one out of that home, then run the move again |
| `is reached through the symlink …` / `… is a symlink` (CLI move) | a session file, a file or folder inside a session's folder, the project memory folder (or anything in it), or a folder above them is a symlink; on Windows a directory junction (or another reparse point) counts as one. The tool never follows one, and nothing was changed. Replace the link with what it points to; for the memory, `--no-memory` moves the session without it |
| `… escapes … (it resolves outside that home)` (CLI move) | a session file or the project memory leads outside the home. A last check: the link checks (symlinks, and on Windows junctions) normally refuse first. Nothing was changed. Replace the link with what it points to; for the memory, `--no-memory` moves the session without it |
| `is … (not a regular file or folder)` (CLI move: a FIFO, a socket or a device file) | a session's folder, its project memory, or the place in the target home where a file would go holds a named pipe, a socket or a device file. The tool never opens one (reading a named pipe can wait for ever) and never copies one. Nothing was changed. Move that file away, then run the move again; for the memory, `--no-memory` moves the session without it |
| `… resolves to …, outside …` (CLI move or rollback) | a folder of the home being written to (the target of a move, or the source home a rollback moves back into) is a link that leads outside that home, so the session would land somewhere else. Nothing was changed. Replace the link with a real folder (move what it points to there), then run it again |
| `… in … is a symlink` (CLI move or rollback) | a folder or file of the home being written to is a symlink (on Windows also a directory junction), even one that leads back inside that home: the tool never writes through a link. Nothing was changed. Replace the link with a real folder, then run it again |
| `The real run would REFUSE: …` (a dry run, exit 1) | the dry run found a reason the move cannot go ahead (the `REFUSE` lines above it). Nothing was written. Fix that, then run the dry run again |
| `the move stopped while … It was undone: nothing was changed` | a CLI move hit an error (a permission, a full disk, Ctrl-C, a `kill`, a closed terminal) and put back every item it had moved; it says so only after checking that each one is back as it was. Fix the cause the message names, then run the move again |
| `undoing it did not finish … The archive … is kept` | the CLI move failed and could not put everything back, or could not confirm that every item is back as it was (the `NOT undone` lines say which). Fix the cause, then run the printed `ccd-rehome rollback`: it moves back what is in the target and skips what never left |
| `kept the copy of …: its original … is no longer in …` / `kept copied memory …: its original … is no longer in …` (rollback) | not an error: the original was deleted after the move, so that copy may be the only one left, and rollback keeps it. Delete it yourself only once you are sure you do not need it |
| `is in both cli and cli:work` (rollback) | an item of the session is in both homes, so rollback cannot tell which one to keep. Compare the two, move one of them away, then roll back again |
| `rollback stopped while …` | fix the cause, then run the same rollback again: it moves back what is still in the target and skips what is already back |
| `this rollback takes it back to …, so that window cannot open it` / `this rollback removes the copy there, so that window cannot open it` (rollback, after `warning: … is shown by Desktop profile …`) | not a refusal: the rollback put back the state from before the move (the undo a move prints always works), and that takes the conversation out of `~/.claude`, or removes its copy there, while a Desktop window lists it. To give that window its conversation back, run the copy the warning prints (`ccd-rehome move cli:work --only ID --to-profile cli --copy`; the other home keeps its own) |
| `not an archive name` / `no cli-move archive named …` (rollback) | that name is not an archive of a move from or into this CLI home. `ccd-rehome status cli:work` shows the newest three (newest last) and how many there are; `ccd-rehome status cli:work --json` lists them all; every move also prints its own |
| `archive name … is ambiguous` (rollback) | two CLI-move archives of that name involve this home. Roll back from the move's other home instead (`ccd-rehome rollback cli ARCHIVE` rather than `cli:work`, or the reverse) |
| `no complete archive at …` (rollback) | that archive was cut off while it was being written, which is before the move changed anything: there is nothing to undo. `ccd-rehome sessions cli` shows where the session is |
| `already there in …; skipped` | the target already has a byte-identical transcript. No error: that session was skipped |
| `older than N days (cleanupPeriodDays …)` / `older than N days (desktopSessionCleanupPeriodDays …)` / `… was last continued in Claude Desktop: Claude Code 2.1.248 and later keep such a transcript …, so it is not re-dated` / `…, and --keep-dates keeps that date: … would delete it at its next start` (refused) / `… would delete the copy at its next start` (`--copy`) | the target home would delete the transcript at its next start. The tool re-dates it, with the files of its sidecar folder (`subagents/`, `tool-results/`, `mcp-tasks/`, `workflows/`), but that only postpones the deletion: the target deletes it again after N days without new activity there (opening it in Desktop without a new turn does not count). After a move (not `--copy`) the source no longer has it, and the archive holds no copy, so the warning says so: use `--copy` to keep it in the source too, which matters most when the source is a backup home. A move with `--keep-dates` of such a transcript is refused (it would be deleted at the target's next start, and nothing else would have it): for such a transcript `--keep-dates` goes ahead only with `--copy`, and then the copy keeps its old date and the warning says the target would delete the copy at its next start (the source keeps its own). On a `--copy` the tool re-dates the copy, never the source. The limit is the shortest `cleanupPeriodDays` or `desktopSessionCleanupPeriodDays` set in the target's `settings.json` (30 when it sets no `cleanupPeriodDays`), in the server-managed settings cached in its `remote-settings.json`, in `managed-settings.json` (`/etc/claude-code/` on Linux, `/Library/Application Support/ClaudeCode/` on macOS, `C:\Program Files\ClaudeCode\` on Windows) or in a drop-in file of the `managed-settings.d/` folder next to it, and the message names where it is set. The tool takes the shortest on purpose: Claude Code combines these sources by rules the tool does not model, so the tool may warn about a transcript Claude Code would keep, never the other way round. A conversation last continued in Claude Desktop is kept at any age by Claude Code 2.1.248 and later, unless `desktopSessionCleanupPeriodDays` is set (then the warning names that limit) or managed settings set `cleanupPeriodDays` (then that applies to it too). Claude Code before 2.1.248 deletes it after `cleanupPeriodDays`, so a move or a `--copy` of one older than that reads `claude --version`: 2.1.248 or later, it is not re-dated (`… so it is not re-dated`, and after a move the source still no longer has it; on a `--copy` a note says that Claude Code before 2.1.248, and any version under the HIPAA configuration, which the tool cannot read, deletes it after `cleanupPeriodDays`); older, or no version known, it is re-dated (on a `--copy`, the copy) and the warning says which version it saw |
| `different organizations … unverified` | the two CLI homes are signed in to different orgs; continuing may have its signed thinking rejected. Sign the target in to the same org to be safe |
| `is signed out (no login file)` / `is signed out (its login file .credentials.json is empty)` (CLI move, a warning) | the target home has no login yet (an empty login file holds none). Start Claude Code in it and sign in (`CLAUDE_CONFIG_DIR=~/.claude-work claude`) before you resume the moved sessions there |
| `is not a Claude Code config dir (no projects/, .claude.json, .credentials.json or settings.json), or it is a Desktop profile` | `cli:NAME` names a folder `~/.claude-NAME` that does not exist, has none of `projects/`, `.claude.json`, `.credentials.json` and `settings.json`, or is a Desktop window folder (it has a `config.json`). A path prints other messages: `… does not exist` or `not a Desktop profile (no config.json)` when it names what a command works on, `--to-profile '…' is not a CLI home` when it is a CLI move's target, and `is your home folder …` (below) for your home folder. Check the name with `ccd-rehome profiles`. A new home exists once Claude Code has started in it: `CLAUDE_CONFIG_DIR=~/.claude-work claude` |
| `--to-profile '…' is not a CLI home` (CLI move) | the target is a Desktop window (its name or its folder) or a folder that is no config dir. A conversation moves only between CLI homes: name one (`cli`, `cli:NAME` or its path; `ccd-rehome profiles` lists them). To show the session in a Desktop window instead, give it a record: `ccd-rehome register PROFILE --cli-session-id ID` |
| `--to-profile names the same CLI home` | the source and the target are the same home: there is nothing to move |
| `moving sessions out of … needs --to-profile P2` | name the home to move to: `ccd-rehome move cli --only ID --to-profile cli:work` |
| `--only … matches N sessions in …` / `--project … matches no session in …` (CLI move) | the id prefix fits no session or several, or no session started in that folder. `ccd-rehome sessions cli` lists them with their folders; use a longer prefix |
| `bad CLI home name` | `cli:NAME` cannot contain `/`, `\` or `:`. For a home anywhere else, give its path |
| `--to-profile is a CLI home` (a Desktop window's `move`) | a Desktop window's records move only to another Desktop window. To continue the session in a terminal, `ccd-rehome resume-cli PROFILE --only ID`; to move its conversation to another CLI home, `ccd-rehome unregister PROFILE --only ID`, then `ccd-rehome move cli --only CLI_ID --to-profile cli:work` (the record id is what `unregister` takes; the move takes the conversation's CLI id, which `ccd-rehome sessions PROFILE --json` shows as `cli`) |
| `… works on a Desktop profile; … is a CLI home` | `quit`, `launch`, `verify`, `register`, `resume-cli`, `unregister`, `export-record` and `adopt` are for Desktop windows. For a CLI home use `profiles`, `status`, `sessions`, `rehome`, `move` or `rollback` |
| `is not on this machine (no ….jsonl in any known CLI home)` (`resume-cli`) | the window's record points at a conversation that no CLI home the tool knows holds: it was made on another machine, or it is in a home the tool was never told about. Name that home once (`ccd-rehome status /path/to/home`) and re-run; a session from another machine comes over with `st-bundle` ([other-machines.md](other-machines.md)) |
| `is your home folder …` / `is a folder above ~/.claude` / `holds the Desktop profile …` / `is or holds ~/.claude-instances, where the Desktop profiles live`, each followed by `: it is not a Claude Code config dir. Name the config dir itself` | that folder can never be a CLI home (your home folder keeps `~/.claude.json`, which made it look like one). Name the config dir itself: `cli`, `cli:NAME`, or its path |
| `there is no other CLI home yet` (`status`, `rehome cli`) | you have only `~/.claude`. Start Claude Code once with `CLAUDE_CONFIG_DIR=~/.claude-NAME claude`, sign in there with the other account, then copy the sessions there: `ccd-rehome move cli --to-profile cli:NAME --copy` (`~/.claude` keeps its own) |
| `… has the same account as …: these sessions need no move to be used with it` (`status`, `rehome cli:NAME`) | every other CLI home is signed in to (or last used) the same account, so a copy there switches no account and the tool advises none. To use the sessions with another account, make a home for it as in the row above |
| `the account of … is not known, so whether … is another account cannot be told` (`status`, `rehome cli:NAME`) | a home has no account in its `.claude.json` (a copy of `~/.claude` made with `cp -a` or `mv` has none: the default home keeps its account in `~/.claude.json`). The command printed is a `--copy`, so the source keeps its own; run it only if you want the sessions in that home |
| `whether … is signed in cannot be read here` (macOS) | the login is in the Keychain, which the tool never reads. If `claude` asks you to log in in that home, do it before resuming |
| `that conversation lives in …, but Desktop looks for its conversations in …` | `register` files only a conversation in `~/.claude`, where Desktop looks (the tool cannot see whether a window was started with `CLAUDE_CONFIG_DIR`). Run the printed `move … --copy` (a copy into `~/.claude`; the other home keeps its own), then run the `register` again. A conversation in `~/.claude` is always accepted; when the window's other conversations are mostly in another home, a note says what that would mean |
| `` `cli` is ambiguous here `` | a Desktop window folder `cli` in a profile root (`~/.claude-instances/cli`, say) is named `cli` too. Use the path the message prints: `~/.claude` for the CLI home, `~/.claude-instances/cli` for the window. (`cli:work` is never ambiguous with a window: a window folder `cli-work` is named `cli-work`) |
| signed in, but the Code tab stays empty or the app seems frozen | quit (or force-close) and start it again: on some builds the sign-in only lands on the next start |
| after upgrading the Raspberry Pi package, Desktop hangs or is signed out | see [get-claude-desktop.md](get-claude-desktop.md): the keyring line |

## Between machines (`st-bundle`, `st-verify`)

| You see | Do |
|---|---|
| `NOT VERIFIED: do not import` | the file was damaged or changed on the way: copy it again |
| `the destination filesystem is case-insensitive and the bundle has name collisions` | two project files differ only in case. Rename one on the original machine and export again |
| `exclude … is unanchored` / `has no justification` | write it as `'/folder/  # why'` |
| `names Windows cannot store` | a project file name is not valid on Windows (for example it contains `:`). Rename it on the original machine |
| `REFUSING to mint the Desktop session while that instance is running` | quit Desktop on this machine and re-run the import; it is safe to re-run |
| `No conversation found` when resuming | start `claude --resume` from the `--dest-root` folder you gave the import |
| verify: `origin proof … CHANGED` | something wrote to the conversation on the original machine after the export: export again |
| verify: `GROWN` | the session was used on the original after the export: the copies have forked |
| the session opens, but the model was rejected | the new machine's Claude Code is older than the one that wrote the session: update it |
